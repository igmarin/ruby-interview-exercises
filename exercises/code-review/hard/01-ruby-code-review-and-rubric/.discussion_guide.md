# Discussion Guide — Ruby Code Review & Rubric

## Expected analysis points

### 1. Potential N+1 query and missed eager loading
- `Order.where(user_id: @user_id)` loads the order rows in one query, but if `item_name` or `price` come from an association (e.g. `order.item.name`), each iteration can fire another query.
- If this report is generated inside a loop over many users, the method becomes an N+1 query per user.
- Use the `user.orders` association and, when needed, eager-load related data with `includes(:item)` or `preload`.
- For very large result sets, consider `pluck(:item_name, :price)` to avoid AR object allocation, or stream/paginate the output.

### 2. Inefficient `+` string concatenation in a loop
- `result = result + "..."` allocates a new `String` object every iteration, making the report building O(n²) in the number of orders.
- Prefer one of:
  - `result << "..."` (in-place append)
  - `lines = []` followed by `lines.join("\n")`
  - a heredoc with interpolation
  - `StringIO` for streaming output

### 3. No input validation on `user_id`
- `@user_id` may be `nil`, a non-numeric string, a negative number, or an unexpected object.
- `User.find(@user_id)` will raise or produce surprising behavior with invalid input.
- Validate with `Integer(user_id.to_s, 10)` and a positive-number check, or a strict regex, before querying.

### 4. Possible nil and missing-record handling
- `User.find` raises `ActiveRecord::RecordNotFound` for a missing user. A report builder usually wants to render "not found" rather than propagate an exception.
- `user.name` or `order.price` may be `nil`, leading to blank output.
- Use `find_by` plus a nil guard, or `rescue ActiveRecord::RecordNotFound`, and handle missing/blank data explicitly.

### 5. `Order.where(user_id: @user_id)` vs `user.orders`
- Repeating the foreign key duplicates the association logic and can drift from the domain model.
- `user.orders` expresses the relationship and lets the association handle scope, eager loading, and future changes to the relation.
- If you need a repository abstraction, wrap `Order` behind an injected scope rather than calling the global constant directly.

### 6. Global-ish `User`/`Order` models
- Hardcoding `User` and `Order` couples the class to global state and makes isolated unit tests awkward.
- A more testable design injects the user scope (and optionally an order scope) as dependencies.

### 7. Method length and SRP
- `build` fetches data, validates input, and formats output all at once.
- Splitting it into `valid_user_id?`, `load_user`, and `format_report` makes the class easier to read, test, and reuse.

## Trade-offs and edge cases

- `find` vs `find_by`: `find` raises and is appropriate when a missing record is exceptional. `find_by` returns `nil` and is better for user-facing reports.
- `pluck` vs AR objects: `pluck` is faster and uses less memory for scalar reports, but it bypasses model methods and cannot eager-load associations.
- Authorization: input validation is not the same as access control. Ask how the caller proves they may view this user's data.
- Large reports: an enormous order list can still exhaust memory. For very large reports, stream rows or paginate.
- `to_i` vs `Integer(...)`: `to_i` silently returns `0` for `"abc"`, while `Integer` raises on malformed input.

## Suggested rubric

| Level | Description |
|-------|-------------|
| **Strong** | Identifies 5+ of the expected points (N+1, string concat cost, input validation, nil/missing record handling, SRP, global model coupling); proposes concrete refactors; discusses trade-offs such as `pluck` vs AR objects and `find` vs `find_by`. |
| **Good** | Finds the major performance and design problems (string concat, validation, nil handling, SRP) and offers sensible refactors. |
| **Needs work** | Only spots surface issues, misses performance/security/design concerns, or proposes refactors that introduce new bugs. |

## Refactored version

```ruby
# frozen_string_literal: true

class UserReport
  def initialize(user_id)
    @user_id = user_id
  end

  def build
    return "Invalid user ID" unless valid_user_id?

    user = User.find_by(id: @user_id)
    return "User not found" unless user

    lines = ["Report for #{user.name}"]
    user.orders.each do |order|
      lines << "- #{order.item_name}: #{order.price}"
    end

    lines.join("\n") << "\n"
  end

  private

  def valid_user_id?
    return false if @user_id.nil? || @user_id.to_s.strip.empty?

    Integer(@user_id.to_s, 10).positive?
  rescue ArgumentError, TypeError
    false
  end
end
```

### Notes on the refactor

- `find_by` plus a nil guard replaces `User.find` and avoids raising on a missing user.
- `Integer(@user_id.to_s, 10)` is stricter than `to_i` and rejects malformed input.
- `lines.join("\n")` builds the final string once instead of once per order.
- `user.orders` uses the ActiveRecord association instead of repeating the foreign-key lookup.
- If `item_name` or `price` live on associated records, replace `user.orders` with `user.orders.includes(:item)` or use `pluck` as appropriate.

## Optional: more testable variant with dependency injection

```ruby
# frozen_string_literal: true

class UserReport
  def initialize(user_id, users: User)
    @user_id = user_id
    @users = users
  end

  def build
    return "Invalid user ID" unless valid_user_id?

    user = @users.find_by(id: @user_id)
    return "User not found" unless user

    lines = ["Report for #{user.name}"]
    user.orders.each do |order|
      lines << "- #{order.item_name}: #{order.price}"
    end

    lines.join("\n") << "\n"
  end

  private

  def valid_user_id?
    return false if @user_id.nil? || @user_id.to_s.strip.empty?

    Integer(@user_id.to_s, 10).positive?
  rescue ArgumentError, TypeError
    false
  end
end
```

This version removes the hardcoded global `User` constant. `Order` is reached through `user.orders`; for unit tests, pass a user double whose `orders` method returns a stubbed collection.
